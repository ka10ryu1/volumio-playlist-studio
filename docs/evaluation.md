# 精度評価

Jev の判定結果をそのまま採用せず、本当に好みに合ったプレイリストを作れるかを確認するための手順と指標をまとめる。

## 評価データの作り方

1. 精度評価画面の「評価対象を追加する」で、30〜50 曲を無作為に選ぶ（seed を指定すれば同じ曲が選ばれる）
2. 選んだ曲は追加時に「調整用（tuning）」と「検証用（holdout）」に半分ずつ分ける。一度決めた用途は変わらない
3. 曲ごとに、判定結果を見ながら次を入力する
   - ジャンル・ムードの判定が「正しい」「誤り（正しい値を選ぶ）」「判定保留（人でも判断できない）」
   - 属性（リラックス度、エネルギー感など）の 5 段階評価（評価しない属性は空欄のまま）
4. 評価は、評価時に表示していた分類結果の写し（エンジン・バージョン・判定内容）と一緒に保存する。分類結果は同じバージョンでも再分類（音響解析の後など）で上書きされることがあるため、何を見て評価したかは写しで追跡する。人手の正解は分類結果とは独立に保存するため、モデルや判定基準を変えた後も同じ評価データで再検証できる
5. 未評価の曲では正誤の選択を空にしてあり、選ばないと保存できない。評価済みの曲を開き直すと保存済みの評価が入力欄に入るため、メモや 5 段階評価だけを直しても正解は変わらない

人手で修正したジャンルは、プレイリスト生成でも分類結果より優先して使う。

## 過学習を防ぐ

- ルールの正規化範囲や Jev の閾値を調整するときは、**調整用のデータだけ**を見る
- 調整の効果は**検証用のデータ**の指標で確認する。検証用の結果を見ながら調整を繰り返さない
- 評価データを追加する場合も、追加時に同じ割合で分割される

## 指標

| 指標 | 定義 |
|---|---|
| ジャンル一致率 | 人手の正解がある曲のうち、エンジンが判定した（保留にしなかった）曲で正解と一致した割合 |
| ジャンル保留率 | 人手の正解がある曲のうち、エンジンが判定保留にした割合 |
| ムード一致率・保留率 | ジャンルと同様 |
| 属性の誤差 | 人手の 5 段階評価を 0〜1 に換算（1→0、3→0.5、5→1）し、エンジンのスコアとの平均絶対誤差。両方の値がある曲だけで計算する |
| 誤判定の傾向 | 誤判定した（正解, 判定）の組み合わせの多い順 |
| 不適切な曲の割合 | 満足度を入力したプレイリストに含まれた曲のうち、「雰囲気に合わなかった」とした曲の割合（分類結果の種類ごと） |
| 主観的満足度 | 保存したプレイリストの満足度（1〜5）の平均（分類結果の種類ごと） |

人が「判定保留」とした曲は一致率の分母に含めない。一致率は判定した曲だけで計算するため、保留率と合わせて見る（保留を増やせば一致率は上がりやすい）。

## Baseline との比較

タグと単純なルールによる分類（ルールベース）を Baseline とし、同じ評価データで Jev と比較する。比較する際は次を確認する。

- 検証用データで、ジャンル・ムードの一致率と属性の誤差が改善しているか
- 保留率が増えすぎていないか
- 実際に生成したプレイリストで、不適切な曲の割合が下がり、満足度が上がっているか（設定画面で選曲に使う分類結果を切り替えて、それぞれプレイリストを作って評価する）

## Essentia を検討する条件

次のような明確な問題が確認された場合に限り、Essentia（または Essentia＋Jev）の検証を検討する。この段階では導入しない。

- Jev を使っても、検証用データでのムード一致率や属性の誤差が改善しない
- 誤判定の傾向が、タグがない曲や音響的な特徴（例: 静かなのに激しいと判定される）に集中している
- プレイリストに不適切な曲が混入する割合が、実用上許容できない

比較では精度に加えて、1 曲あたりの解析時間、CPU 負荷、メモリ使用量、導入の難しさ、モデルのライセンスを記録する（[architecture.md](architecture.md)）。

## CSV 出力

評価結果は CSV（UTF-8、BOM 付き）で保存できる。各エンジンの判定結果、人手の正解・正誤、5 段階評価を含む。表計算ソフトで開いたときに数式として実行されないよう、`=`・`+`・`-`・`@` で始まる値の前には `'` を付ける。CSV には曲名などの利用者固有のデータが含まれるため、リポジトリや Issue に貼らないこと。
